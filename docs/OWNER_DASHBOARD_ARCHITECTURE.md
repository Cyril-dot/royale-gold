## 1. What exists today

### 1.1 Stack
Next.js 16 (App Router, `cacheComponents` per repo `AGENTS.md` — read
`node_modules/next/dist/docs/` before writing Next code) + TypeScript +
Tailwind + Prisma 7. Postgres in production (Neon); local dev uses a
**sqlite stand-in schema** (`prisma/schema.sqlite.prisma`, generated by
`scripts/make-sqlite-schema.mjs` — never edit by hand). **Trap:** the sqlite
schema stores money as `Float`, production as `Decimal(12,2)` — local
arithmetic is never proof of production behaviour. `DATABASE_URL` env only.
No `vercel.json` (no Vercel cron config), no test suite, no middleware file.

### 1.5 Auth, roles, security
3 roles (`owner`/`admin`/`user`, `prisma/schema.prisma:16-20`). JWT cookie
`rg_session`, HS256, 7 days, `httpOnly`, `sameSite: lax`, `secure` only in
production. `getSessionUser` loads the DB user (rejects inactive accounts
and stale `sessionVersion`); `requireRole` is exact-match — owner implies
nothing. Admin per-section RBAC: 16 sections (`src/lib/rbac.ts`).
TOTP 2FA is opt-in for admin/owner, never enforced; no backup codes.
**Gaps (do not re-introduce):** no `middleware.ts` (new routes must add the
guard); logout / password change do **not** bump `sessionVersion` (stolen
tokens survive); `POST /api/auth/login/totp` needs no proof the password
step ran; no CSRF protection; no security headers in `next.config.ts`;
no rate limiting; passwords bcrypt cost 10, min length 6 only.
Kill switch (`globalKill`) is server-enforced in play/cashout/settle;
**maintenance mode is client-only** (no server route checks it).
Audit: inline `prisma.auditLog.create` in 53 files, append-only by
convention; gaps — admin creation, referral-code creation, campaign-draft
creation, all auth events unaudited. Gateway secrets AES-256-GCM + last-4
masks; **MoMo/bank numbers are stored and shown in full everywhere**
(owner Payouts, withdrawal snapshots, CSV) — masking is a Phase 2/6 decision.

### 1.6 Money safety (read the ChurchOS principles — they apply here)
ChurchOS `AGENTS.md` (§3–4) is a different product (church bookshop POS) and
its scope does **not** transfer — but its money-safety principles do, and the
brief §1/§22/§30 demands the same: integer/decimal money, one transaction
per financial write, idempotency where a duplicate harms, never delete posted
history (reverse with reason + actor), server-side auth, no invented values.
Current state vs those principles:
- Storage is `Decimal(12,2)` (53× Decimal, 0× Float in Postgres) — good.
- **Arithmetic is JS float in flight** (`round2`, `dec()` → number;
  `src/lib/money.ts:5-17`). Rounding happens per step, not once at
  settlement. Safe-ish at this scale; not integer-minor-unit safe.
- **Ledger is a computed view, not a table** (`src/lib/ledger.ts` merges 6
  sources, capped 200 rows/source). Deleting a source row erases it.
  **Known flaw:** withdrawal rows count as `−amount` in `cashOut`
  regardless of status — pending/rejected/held withdrawals inflate it.
- **Idempotency exists only for PayTeller** (unique `reference` + atomic
  claim + webhook-event PK). Demo deposits, conversions, adjustments,
  settlements, payouts have no dedup key.
- No refunds/reversals as a flow (only the Payouts-tab delete + audit).
- No FX, no settlement import, no cron/scheduler of any kind.

## 2. Financial source of truth (summary — full definitions in the metric doc)

| Concern | Authoritative source | Notes |
|---|---|---|
| Deposits | `DepositEvent` | `amount`, frozen `pctInForce` + `commission`, `fiatCurrency`, `providerPayload` |
| Gateway lifecycle | `PaytellerPayment` + `PaytellerWebhookEvent` | Unique `reference`; wallet credited full principal; house absorbs 10% |
| Withdrawals | `Withdrawal` | Request only — no money moves; statuses pending/approved/admin_approved/rejected (+ untyped `held`) |
| Payout destination | `WithdrawalAccount` (1 per user) | Snapshotted onto each request |
| Commission owed | Recomputed (`src/lib/commission.ts`) | Rules engine (RevShare/Turnover) + legacy fallback; never stored |
| Commission paid | `CommissionPayout` | Sum of rows; balance = owed − paid; no status column |
| Game P&L / GGR / RTP | `GameResult` | Cash and coins kept apart; fiat on every row |
| Balances (current) | `User.cashBalance` / `simBalance` / `coins` | No balance-history table |
| Adjustments/bonuses | `BalanceAdjustment` | Atomic with balance change + audit; kind adjustment/bonus/promo |
| Proof | `AuditLog` | Append-only by convention; action vocabulary in schema comment |
| Config | `CurrencyConfig` (per fiat), `GatewaySettings`, `PlatformSettings` | Singletons `global`; GHS rows kept in sync |

Rules that must survive every phase: aggregates **never sum across fiats**;
**UTC calendar days** (`todayStr()`); "paid out" = `Withdrawal.status =
"approved"` (there is NO paid status — see §7 decision 2); commission is
recomputed, never double-counted; **never label deposits − payouts as
profit** (P&L net profit = GGR − commissions owed, `src/app/api/owner/pnl`).

## 4. Phased implementation plan (dependency order)

### Phase 1 — Date-range + KPI comparisons + charts
Global date state (presets Today/Yesterday/Last 7d/Last 30d/This week/Last
week/This month/Last month/This year/Custom) driving every date-sensitive
section; previous-equivalent-period comparison on every KPI; toggleable
financial-performance chart series (deposits / payouts / commission
generated / commission paid / revenue / liabilities) with daily/weekly/
monthly grouping; user-growth chart; KPI tiles become drill-down links.
Extend `dashboard-stats` (or one new `overview` endpoint) — one call,
per fiat, UTC boundaries, comparisons labelled when a period is incomplete.
**Blockers:** none technical. Decisions: reporting timezone (UTC now —
keep or configure Africa/Accra); "profit" wording rule stands.

### Phase 2 — Payout calendar + beneficiary detail + commission center
Month/week/day/list payout calendar with per-day summary cards and the
brief's status colours (never colour-alone); beneficiary detail as a
full-screen mobile view / drawer with masked account details by default,
access audit, status-history timeline; commission table (beneficiary,
source transaction, rule/rate, gross basis, amount, earned date, status,
settlement reference) + beneficiary totals + payment batches.
**Blockers:** withdrawal "paid" semantics (decision 2 — a `PAID` status needs
a migration; until decided, "confirm paid" can only be a labelled manual
attestation); masking policy (decision 5); no real money movement —
manual "mark paid" must be labelled as an administrator attestation, never
as gateway proof (brief §7.4).

### Phase 3 — Reconciliation + gateway monitoring + risk/alerts
Gateway health dashboard per provider from real transaction evidence
(success rate, error trends, last success, payout counts — never "healthy"
because the app is reachable); reconciliation discrepancy workflow
(severity, internal record, external reference, amount difference, assignee,
resolution notes, audit) — internal-only until a feed exists; alert
workflow (assignee, open/investigating/resolved, notes) on top of the
existing fraud/anomaly/risk-rule engines.
**Blockers:** PayTeller keys not live + no settlement file/format known
(decision 6, Chuks's step); no FX; failed-deposit records don't exist
(demo cashier is synchronous — failures surface only via PayTeller
`PaytellerPayment.status`).

### Phase 4 — Reports/exports + financial center + daily performance
Daily performance table + daily report drill-down; dedicated financial
center (cash-flow chart, daily ledger summary, liabilities view, fees/
provider charges aggregate from `PaytellerPayment` fee fields); report
center (daily/weekly/monthly financial, liabilities, gateway, reconciliation,
risk, audit) with CSV (exists) + Excel + PDF; export metadata (period,
timezone, generated-by, definitions) and masked account details by default.
**Blockers:** Excel/PDF library choice (decision 9 — no new paid infra);
scheduled reports need a scheduler (no cron infra; Vercel cron config is a
deployment decision, not just code).

### Phase 5 — Mobile deep pass + notifications + AI/forecasting decisions
Owner bottom nav (Home/Finance/Payouts/Activity/More, §24.4) replacing the
site dock inside the owner panel; mobile home priority order (§24.3);
bottom sheets for payout/user detail; mobile calendar (agenda-first);
mobile charts with touch tooltips + table alternative; in-app notification
center (owner alerts: payout awaiting approval, overdue, failed txn,
gateway incident, reconciliation discrepancy, commission due, security).
**Blockers:** push needs infra (none exists — decision 11); AI assistant
needs a provider + budget (decision 7); forecasting is optional
(decision 8); light theme is a decision (10).

### Phase 6 — Financial correctness + security audit (brief follow-up prompt 3)
Money hardening (audit every float sum; consider integer minor units or
Decimal arithmetic at the settlement boundary); idempotency keys on demo
deposits/conversions/adjustments/settlements; fix ledger `cashOut`
(pending/rejected/held withdrawals); close the owner single-approve bypass
(decision 3); bind `login/totp` to the password step; logout/password-change
bumps `sessionVersion`; enforce `maintenanceMode` server-side; fill audit
gaps (admin/code/campaign creation, auth events); rate limiting on
login/register/TOTP; CSRF + security headers; sensitive-access audit.
**Blockers:** mostly decisions (2FA enforcement — decision 12; two-person
scope — decision 3). Write the tests this repo has never had (follow-up
prompt 3): commission recompute, GGR/P&L, reconciliation, authz, idempotency.

## 5. Architecture decisions to record (do not improvise during build)
- **No parallel ledgers.** The ledger stays a computed view over the six
  sources unless a stored ledger is explicitly approved — do not invent a
  second source of truth.
- **No invented data.** Every figure cites a table/endpoint (metric doc).
  Empty states are one honest line, never a plausible-looking number.
- **No new paid infra** without Chuks's say-so (AI provider, push service,
  Excel/PDF SaaS, scheduler).
- **No frontend-only financial state changes.** Every status change is a
  server route + audit row.
- **Keep the flat RG design.** New sections reuse `.sum-card`, `.p1b3-bars`,
  `.ow-act-row`, `.ow-payday` patterns; no new palette, no light theme
  unless decision 10 says so.
- **Per-fiat everywhere.** New endpoints take `?currency=` and never sum
  across fiats. New countries need a `CurrencyConfig` row + a decision.
- **UTC days until decided.** `todayStr()` is the day rule; a configurable
  reporting timezone is Phase 1 work, not a silent change.

## 6. Risks already in the tree (do not make worse)
1. Float-in-flight money with per-step rounding; no canonical settle-time rounding.
2. Ledger is derived, not append-only; `cashOut` includes unapproved withdrawals.
3. `approved` ≠ paid — nothing ever moves withdrawal money; the UI must never imply it does.
4. Owner can single-approve any withdrawal (maker-checker bypass).
5. No idempotency keys outside PayTeller; retried requests are new writes.
6. No cron — every periodic financial action depends on a human pressing a button.
7. `Withdrawal.status` is a free `String`; `"held"` is untyped and possible.
8. Mid-day rule creation makes the per-day commission tab and the rollup disagree for that day (code comment, `src/lib/revenue.ts:14-16`).
9. No test suite; no rate limiting; no CSRF; maintenance mode is client-only.
10. Prod DB state is unknown from here — every schema change still needs its SQL run in Neon by Chuks before the code lands live (standing pattern).
